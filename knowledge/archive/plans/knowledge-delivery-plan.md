## 1. 计划目标与原则

本计划以范围基线和总体设计的行为契约为依据，将架构可行性、最小写路径协议与首版能力分别设置验证门。底座试验先确定负载与判定 profile，再用实测确认或否定架构假设；骨架只证明已覆盖的链路，完整首版需要后续里程碑和全项验收。

核心原则是先验证最高不确定性，再实现功能。Spike 允许建立最小逻辑数据模型、故障夹具和实验性有效视图实现，但不交付正式业务接口。骨架不提前实现代码套件、更正、对齐与通用跨来源依赖；来源捕获的操作/尝试/回执子集从 Phase 2 开始具备；Phase 3 扩展为完整任务清单、跨存储候选与发布协议，不能等到恢复阶段再补。

## 2. 风险消除总顺序

按"若不成立则推翻设计"的严重度排序，越靠前越先消除。整个计划以这条主线组织。

| 序 | 待消除风险 | 若不成立的后果 | 消除阶段 |
| --- | --- | --- | --- |

| R4 | 有效视图"物化 vs 实时"的性能差异 | 检索延迟不可接受，写路径需重构 | Spike-2 |
| R5 | zvec 逐项写入、后过滤、重开持久化 | 跨库一致性成本被低估 | Spike-2 |

## 3. 阶段 A：底座验证 Spike

目标是用固定 commit 验证 R1–R5 的架构假设，产出《底座实测结论报告》回填总体设计 §5.1、§5.3、§8；模型质量、完整增量维护和整套资源行为在各里程碑验证。本阶段不实现正式业务接口。

核对版本沿用总体设计：graphdb `9d6e966ef0ae214cff8d5018efe1dafb37bc2a99`、zvec `a4347e31f1b8e216cffba59285427a3b78551229`；Tree-sitter 与 grammar 提交在本阶段选定并记录。

### 3.1 Spike-0 组合打通（消除 R1）

目标：在 `thirdparty/` 下固定 graphdb、zvec、py-tree-sitter 与 Python/C++ grammar，能在同一环境导入并各自运行最小实例。

验收点：

- 三者在同一 Python 环境导入无版本或符号冲突。
- graphdb 建图并跑通一条 Cypher 读。
- zvec 建 collection、写一条、查一条通。
- Tree-sitter 实际解析 Python/C++ 最小样例并检查节点与范围，不能仅以包导入成功代替 grammar/runtime 兼容。
- 记录各依赖的来源、提交、许可证与构建步骤。

产出：可复现的构建脚本，以及版本与许可证清单，作为总体设计 A12 组合兼容验收的前置。

### 3.2 Spike-1 graphdb 关键契约与实测容量范围（消除 R2、R3）

目标：实测内存工作集曲线、提交可见性、同目录可写与多只读持有者的互斥打开及崩溃恢复，并给出无 ALTER/DROP/MERGE 下的幂等写法。

验收点：

- 按已记录 profile 递增图规模，包含来源、修订、片段、证据、声明、支持、人工记录及候选/保留版本，分别记录逻辑对象数、物理节点/边、输入字节与 RSS；给出受实测环境限制的容量范围，不将裸节点数等同可支持文档数。
- 实测 TP commit 后独立 Read 的可见性延迟，确认"发布需核验实际读取路径"的必要手段。
- 触发并复现 CommitOutcomeUnknown，验证"关闭→可写重开→核对发布记录"的恢复流程。
- 验证同目录单 writer / 多 reader 约束，确认只读打开不触发恢复、修复或清理。
- 在无 ALTER/DROP/MERGE 条件下，用"明确身份 + 事务"实现幂等写入，给出至少一个可复用写法样例。
- 用最小控制模型验证：读集变化返回冲突；根发布选择、关联失效、PublicationView 修订与 operation_id 回执在同一图事务中生效；新支持竞争和取消不能造成部分发布。

CommitOutcomeUnknown 的真实触发与适配层未知响应注入分别记录。无法稳定触发真实错误时，注入可以验证核对路径，但底座重开与回执读取仍须真实执行；未覆盖的底座故障窗口不得标为已验证。

产出：实测容量范围、可见性与恢复契约备忘、幂等写法样例；目标档位通过不等于找到容量天花板。

### 3.3 Spike-2 zvec 契约与有效视图性能（消除 R4、R5）

目标：坐实跨库一致性成本与检索性能路径，并给出有效视图物化策略结论。

验收点：

- zvec 批量写入返回逐项状态；构造部分失败，验证"按稳定投影 ID 幂等补写"可行。
- 全文、向量与后过滤（按业务 ID、来源修订、构建版本）实测，确认后过滤能否下推，以及旧候选占据召回名额时的补取成本。
- Embedding 空间标识写入与查询兼容性校验：维数相同但空间不同必须被拒绝。
- 重开 collection 后持久化与查询结果一致。
- 有效视图 micro-benchmark：对同一批数据分别实现"发布时物化选定/争议/排除"与"查询时实时计算"，对比查询延迟与写放大，给出推荐策略。

两版实验使用同一预期结果与最小语义：多来源独立支持、同条件争议、人工替代及撤销、跨来源依赖失效、Scope 裁剪。先校验结果一致，再按同一负载与预算比较延迟、更新/重建成本及峰值空间；只测最终实体属性读取不能代表有效视图性能。实验不要求提前交付 M1 的正式接口。

产出：zvec 适配测试基线，以及有效视图物化策略结论，回填总体设计 §5.3。

### 3.4 阶段 A 交付物与决策门

阶段 A 的交付物是《底座实测结论报告》、试验 profile、可复现脚本和可回归适配层测试。Go 要求 R1–R5 的正确性不变量全部通过、目标档位测量完整且满足预先记录的阈值，读写/恢复契约有可执行实现方案。失败、未测、无法核验或阈值未填写均不算通过；允许继续探索，但不能据此放行骨架。结果只适用于已测环境、版本和负载范围。

当前判定（2026-10-21）：`local-dev-1000-v2` 下 Go，仅放行后续骨架工作。1,000 来源 × 每修订 8 个 1 KiB 片段 × 3 个版本、384 维测试向量；独立 worker 峰值 RSS ≤ 2 GiB、查询 p95 ≤ 200 ms、构建和重开各 ≤ 120 s。10/100/1,000 三档共 18 项试验通过，两套原生故障测试通过，项目回归 82 项通过、无跳过。数据、阈值、资源配置及源码哈希见 [profile](../python-evidence/validation/profile.json)、[结果](../python-evidence/validation/RESULTS.json) 与 [报告](../python-evidence/validation/BASE_REPORT.md)。

适用条件：固定 graphdb 兼容构建变体及 TP 查询预算；使用显式 Read Only 事务，两个旧读者与候选构建/选择更新并存已测。有效视图先采用实时计算；物化仅在后续真实负载证明需要时启用。此结论不证明完整 SDK 发布/恢复已实现，也不消除许可证、真实模型质量、冷启动、断电和未测容量风险。v1 默认查询预算失败保留，v2 显式配置后全量重跑，验收阈值未改变。

### 3.5 正式试验 profile 与判定规则

profile 是试验输入和判定依据，不是 SDK 默认参数。正式用于决策前必须填写实际值并记录版本；本文不预设未经测量的规模承诺或任意数值。可以先做探索测量，再确定正式档位，不能事后按结果移动阈值而保留原通过结论。

| 项目 | 试验前固定的内容 | 必须报告的结果 |
| --- | --- | --- |
| 环境与版本 | CPU、内存、磁盘、OS/架构、Python、依赖提交/构建选项；模型试验补 GPU/显存、实际模型/量化与运行时 | 实际环境、差异与可复现命令，不能混用不同环境结果 |
| 代表性负载 | 文档/代码输入字节、片段分布、逻辑对象与边比例、扇出、多来源/争议比例、修订与候选/旧版数量 | 实际对象数、覆盖样例与未覆盖范围，容量仅按实测档位说明 |
| 资源与操作 | 可接受峰值 RSS、可用磁盘与保留余量、并发查询/构建、更新/重建批次及读取保留场景 | 峰值内存、磁盘/WAL/索引/候选空间、写放大、吞吐及构建/恢复耗时 |
| 检索与有效视图 | 固定查询、top_k/图预算、并发档位、可接受延迟与预期对象/证据 | p50/p95、候选补取与不足、固定结果正确性；近似召回另报，不混作精确完整性 |
| 故障与协议 | 每个持久化边界、中断/取消顺序、预期回执与任务结果 | 不变量全通过；底座实测、适配注入和阻塞/未测分别列出 |
| 模型与检索质量 | 固定标注语料、查询与期望证据、否定/条件/同名样例、准确率/召回率等接受阈值与允许资源 | 实际指标、错误样例、格式/证据/语义分别统计；M1/M5 使用，不能只报告格式通过 |

R2 判定使用代表性知识负载及同时保留当前版、候选版和旧读者的成本；R4 在正确性一致的前提下比较两种策略是否满足相同目标档位。阈值缺失不能通过增加“待验证”注释变成 Go。profile 改变后重新判定受影响结论，结果回填明确实际值和边界，不从小样本外推未测容量。

## 4. 阶段 B：走通骨架纵切片

范围锁定单一 Markdown 来源及其两个修订，验证重复提交、版本替换和旧候选过滤；不实现通用 sources.sync/delete、代码套件、更正、对齐与跨来源依赖处理。目标是验证三存储的写-发布-恢复-查询闭环和 R7 的幂等/兼容基础。实现前的必要设计输入如下，完整字段与物理映射在该阶段收敛：

| 进入阶段 | 必须具备的设计输入 | 验证时点 |
| --- | --- | --- |
| Phase 1 | 库清单、初始化意图、身份/世代检查、格式兼容矩阵、句柄与资源归属、SDK 执行与并发模型（同步接口/JobHandle/worker 池/句柄线程安全） | Phase 1、Phase 5；迁移本体 M4 |
| Phase 2 | 来源最小 Schema、身份/修订、快照映射、重复摄入、操作回执与可替换解析/抽取契约 | Phase 2–3、Phase 6 |
| Phase 3 | 构建目标、必需/可选产物、文档影响集合/读集、稳定产物 ID、图内原子边界、发布回执及阶段持久化顺序；定稿本阶段文档控制 Schema，不提前冻结 M1 领域表 | Phase 3 建立协议和最小故障核对，Phase 5 扩展恢复窗口 |
| Phase 4 | 固定 PublicationView、单向量空间与覆盖、Scope、查询状态及证据契约 | Phase 4、Phase 6；完整组合 M1/M2 |

### 4.1 Phase 1 存储适配窄接口与句柄生命周期

目标：落地 GraphStoreAdapter、SearchIndexAdapter、SnapshotStore 三个窄接口，以及 KnowledgeBase.create / open / close。

实现状态：生命周期与适配层原有 45 项测试已回归通过；这不等于完成 Spike-1 的全部规模、可见性和恢复验证。

验收点：

- create 不覆盖既有非空内容。
- close 回收本进程资源，停止接收工作并在安全边界收束任务。
- 只读 open 不执行任务恢复、修复或清理。
- SDK 不暴露可任意写入的底座连接，不提供绕过发布视图的原始 Cypher 入口。
- create 中断不覆盖已有内容；open 拒绝混用库身份/存储世代及不兼容格式；只读不自动升级。
- 实例有有限任务/批次准入及候选空间检查入口，资源不足与占用可检查，默认值按 profile/详细设计记录。
- 执行模型落地（总体设计 §2.4）：查询同步返回，长任务经 JobHandle 由有限 worker 池执行；句柄进程内可跨线程共享，写路径经进程内发布协调器串行化。

依赖：Spike-1 的幂等写法与可见性结论、总体设计 §8.2 清单契约。对应 A01、A24、A25 的基础子集。

### 4.2 Phase 2 来源注册、摄入与快照

实现状态：已交付来源摄入闭环及可替换处理契约；本阶段交付时属于最小探针通过后的探索交付；后续完整底座试验已在 §3.4 单独判定，不能把两者混作一套证据。可复现脚本、测试和未测项见 [验收记录](../python-evidence/spike_1/PHASE2_REPORT.md)。

目标：分离 sources.register 与 ingest_documents，捕获不可变 UTF-8 原始字节，建立 Source、SourceRevision、完整正文 ContentUnit 及来源摄入回执。只定义 DocumentParser/KnowledgeExtractor Protocol、自有数据类型、阶段指纹与校验辅助函数，不新增解析库或模型依赖。

验收点：

- 来源键和位置分开，重复注册不产生新身份；同键领域或位置不一致返回冲突。
- SourceRevision 使用实际输入摘要，快照保留中文、BOM、CRLF 和空文档；不以 mtime 代替版本，范围为严格左闭右开字节区间。
- 重复摄入仅复用完整成功效果；失败可重试，A→B→A 可复用修订但记录选择变化；处理指纹变化不重建未变快照。
- 不同来源同内容仍有独立修订归属；同来源并发目标不同返回冲突，过期尝试不能提交。
- 快照可靠准备后持久化操作意图；图内原子提交修订、单元、成功回执和最近成功摄入选择，再从实际读取路径确认。
- 提交前取消不改变最近成功摄入选择；提交后迟到取消不覆盖成功。未知提交或确认失败进入 recovery_required，停止实例后续写入，可写重开后按操作 ID 显式核对；只读不恢复。
- 文件路径排除在读取/落盘前执行；字节输入为调用方显式提交，不宣称敏感内容自动识别。快照摘要/长度、元数据、并发安装和越界校验均有测试。
- 两个测试 Parser、两个测试 Extractor 能经同一接口替换；检查类型、位置、证据、预算、取消和错误。测试实现不算实际解析/模型能力。
- 来源检查提供有界列表、修订、正文与快照，ingestions.get/snapshot/reconcile 提供状态/固定输入只读检查与显式可写核对；结果返回 captured/unchanged 和 search_ready=false。

Phase 2 最小物理 Schema 为 1，不迁移 Phase 1 Schema 0，不自动覆盖非空目录。新库 TP DDL 在空闲连接执行，初始化完成后才标记 ready。上述为 Phase 2 交付边界；真实文档解析在 Phase 3 交付，GC、自动续跑、来源删除和知识抽取仍未交付。

风险消除：R7 的来源幂等子集，以及 R3 的串行来源事务/同连接读取/重开核对子集已测；后续 Spike-1 已补充原生未知提交/故障恢复、独立只读者、目标规模及最小原子发布影响模型，详见 §3.4。完整业务影响闭包仍待对应里程碑。格式迁移留 M4，完整跨存储协议留 Phase 3/5。

### 4.3 Phase 3 分段、全文/向量投影与发布

实现状态：已交付本节构建侧子集。实际接口、DDL、状态和资源配置见 [契约](../python-evidence/phase3/CONTRACTS.md)，可执行用例、故障窗口和测量见 [验收报告](../python-evidence/phase3/PHASE3_REPORT.md)。新增 build_documents 与 builds/publications 检查入口，捕获回执保持原语义；Phase 4 search API 仍未交付。

目标：通过 Phase 2 的 DocumentParser 契约接入真实 Markdown 解析适配器，保留章节结构分段，片段保留到原文映射；接入 Embedding 提供者（允许预计算向量）；从第一条正式写路径落实总体设计 §5.7 协议，写候选图产物与 zvec 投影，完成校验、图侧发布与回执原子提交、实际可见性确认。

验收点：

- 分段不丢失来源范围，片段定位指向确定快照。
- 每条投影保存业务 ID、来源修订、构建版本、内容摘要与 Embedding 空间标识。
- 逐项检查批量写入结果，部分失败进入核对与补写。
- 发布通过实际读取路径核验可见性，不以 commit 返回或 checkpoint 代替。
- 未发布候选不进入默认查询；首次构建失败时不伪造空的成功结果。
- 构建目标明确 graph 元数据、全文及向量要求，不能把骨架元数据图报告为实体关系抽取完成。
- 持久化 operation_id、attempt_id、输入/产物/逐项状态及回执；同一来源新修订以版本化产物替换，不覆盖当前读者所用版本。
- 候选准备、批次缓冲与磁盘余量受限，失败产物不会突破既有读取的保留要求。

依赖：Spike-1 原子边界、Spike-2 逐项写入与有效视图结论，以及本阶段进入前已确定的最小恢复协议。对应 A02/A03 构建侧、A04/A09 版本与幂等子集、A08/A24 发布及资源基础。

当前实现保持 schema_version=1，仅 CREATE 追加文档构建表，旧开发库按无历史业务数据的前提显式重建；不迁移、不在 open 中补表。Parser 使用固定纯 Python/MIT 的 markdown-it-py 4.0.0，独立 Segmenter 保留原始 UTF-8 范围；Embedding 使用预计算入口及显式测试提供者。全文/向量双 collection 和原子来源选择已落地，M1 领域对象尚未建表。

实际 SDK 的 10/100 来源、三版数据、384 维测试向量与失败残留负载已按固定 profile 实测；两个旧 Read 的保留范围是一份来源的完整捕获/构建/发布，长 Read 耗尽退役预算另有背压测试。100 来源捕获加构建 117.64 秒、峰值约 577 MiB、只读重开 1.13 秒，包含约 24.3 MiB 的临时索引副本；结果通过当前门槛但耗时余量小，不能外推 1,000 来源或真实模型吞吐。内部发布核验延迟不等于 Phase 4 公共查询延迟。完整实际 SDK 的 1,000 档留 M5。

已将底座缺口转为明确约束：原生只读打开在正常关闭后也可能写文件，正常只读实例改用有预算的私有字节副本，异常会话在可写重开核对前仅检查图/任务元数据；已有投影先 fetch 并复用相同内容，拒绝原地覆盖，只对缺失 ID 补写。原生块合并保留全部版本化 ID，不替代 M4 的 GC。关键 SDK 边界 SIGKILL、真实底座恢复和适配层注入分别记录，原生内部任意故障与 SDK 回执的组合仍需 Phase 5 扩展。

### 4.4 Phase 4 检索闭环与证据回原文

目标：实现 search（text / vector / hybrid，RRF 融合）与 evidence.get；固定图侧发布视图，候选回图复核。

验收点：

- 全文与向量分别召回，按业务对象去重后以 RRF 融合，保留不同来源与通道贡献。
- 证据定位构建时快照，字节/行列与内容一致；原文不可用时明确报错，不读取当前外部文件冒充旧版本。
- 结果统一包含 items、publication_view、execution 与 diagnostics。
- 底座报错不当成无命中；近似召回、截断与候选不足如实标注。
- 固定一个向量世代及其覆盖；不兼容向量和未覆盖请求范围明确报错，显式退到全文时记录实际执行通道。
- 两个修订之间正在读取的查询保留原视图，后续查询排除旧候选；执行说明记录版本过滤及补取原因。
- 错误按总体设计 §7.4 分类返回，携带码、阶段与可重试性；能力未配置/未就绪、版本不兼容、预算超限与需恢复可区分。

对应总体设计 A02、A03、A10、A17 的骨架子集。

### 4.5 Phase 5 关闭重开与基础恢复

目标：验证 Phase 3 已实现的持久化协议；写路径中断后可核对恢复，关闭重开后来源、证据与发布状态保持。

验收点：

- 重开可写实例先核对底座、未完成任务与当前发布记录，再允许恢复工作。
- 发布前中断保留上一版并报告本次未生效。
- 发布后任务状态未写完时，以已确认的发布记录恢复任务结果，不重复构建。
- 模型调用结果不确定时不自动重放，重试须列出可能重复的外部操作。
- 按总体设计 §5.7 的所有边界注入中断：快照孤立、调用未知、候选部分完成、已就绪未发布、发布后确认丢失、提交结果不确定；真实底座恢复与注入证据分别记录。
- 发布回执可按 operation_id 查回，即使来源已有下一次发布；取消与发布竞争按实际结果恢复，不把已生效操作恢复为 cancelled。
- 读取保留与清理竞争不删在用产物；不完整初始化与不兼容打开能识别且不隐式改写。

对应总体设计 A01、A08 的骨架子集。

### 4.6 Phase 6 骨架端到端验收

目标：用一套固定 Markdown 资料与预期结果跑通全链路。

验收点：

- 创建→摄入→检索→证据→关闭重开→再检索，结果一致且可回原文。
- 追加重复摄入、同一来源 v1→v2、旧视图读取、旧候选排除与不兼容向量请求；首次失败与成功无命中分别识别。
- 回归 Phase 3/5 的全部协议边界，包含发布后终态丢失及取消竞争，不能只保留发布前中断两个样例。
- 给出该切片的延迟、峰值内存与当前/候选/保留空间，按 profile 判定；结果只验证该切片，不将单文档内存数替代整个知识负载的容量结论。

产出：可回归的端到端样例，作为总体设计 A12 组合验证的首个真实闭环。

## 7. 测试架构

验收项 A01–A27 通过分层测试落实，纯 mock 不得替代真实底座的组合验收（总体设计 §9）。

| 层级 | 范围与底座 | 主要覆盖 |
| --- | --- | --- |
| 单元 | 纯逻辑，mock 存储适配层 | 身份/幂等键、影响集合与读集计算、有效视图选择、Scope 裁剪、错误分类映射 |
| 集成 | 真实 graphdb+zvec+快照，固定 commit | 逐项写入与补写、发布与可见性核验、格式兼容与打开拒绝、向量世代与覆盖 |
| 端到端 | 真实三存储组合 | A01–A27 的场景流程，含关闭重开与断网本地模型流程 |
| 故障注入 | 真实底座 + 适配层注入 | §5.7 每个中断边界；底座真实恢复、适配注入与未覆盖窗口分别报告 |

CI 须能构建 submodule 并跑真实 graphdb+zvec 的集成与端到端层；无法在 CI 稳定触发的底座故障（如 CommitOutcomeUnknown）以适配层注入覆盖核对路径，但底座重开与回执读取仍须真实执行，未覆盖窗口显式标注为未验证。

固定标注语料、预期结果、故障用例与 §3.5 的 profile 阈值纳入版本管理，与所用底座提交绑定；profile 阈值改变后重新判定受影响结论。测试数据规模按代表性负载选取，不从小样本外推未测容量。夹具与数据集的管理方式、CI 资源规格在详细设计确定。
